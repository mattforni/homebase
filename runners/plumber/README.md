# The Pipeline Runner

Pulls the portal, both mailboxes, the One Pager and the candidate sites, runs the `plumber` agent headlessly over what was pulled, so the week's roster is built before the Tuesday desk block opens, commits the roster into the Atelic repo, and mails a report as `YYYY-Www Pipeline` that links it. Runs on Cloud Run as the job `plumber`, Mondays 22:00 Denver; `bin/runner/run-local plumber` is the way to iterate on it.

**The runner fetches; the model reads** (ATE-551, 2026-09-15, the recruiter's shape from ATE-543). Until then the agent did every read itself, one `hs` or `gws` command per model turn, walked sites in a browser, and a pass cost 7.54 USD on Opus; the fetching was most of the bill. Now the entrypoint pulls before `claude -p` starts:

- **The repos.** Eudaimonia and, inside it, the Atelic repo: the checkouts on this machine (mounted read only into the container by `mounts`), or in production two shallow clones over read only deploy keys. The method, the three rules, the Voice samples, last week's roster, this week's skeleton with its Placed Ahead entries, and the `Leads/` audits are all read from there.
- **The portal.** `lib/hubspot.mjs sweep`, the same client and joins the retro's `week` command uses (the file moved into `runners/lib/` for exactly this). Every funnel company with its GROW fields, every contact carrying a Lead Status, every logged email of the last 120 days with its opens, every open task, and the meetings and notes of the last sixty days with their bodies, Granola links included. The day counts, the touches run, the opens read asymmetrically, and the section each name lands in are computed in code and written to `portal.md` as tables, with every name's logged sends and replies in `portal-detail.md` (read per name, never whole) and `portal.json` beside it. The sweep also writes `sites.txt` and `mail-terms.txt`, the lists the next two pulls read.
- **The mailboxes.** `lib/gmail.mjs`, both mailboxes through the Gmail API with the two vaulted `authorized_user` JSONs, searched for every funnel domain and address over sixty days, with the bodies of incoming mail from the last three weeks. Each mailbox runs a control query first, so an empty result from a broken read fails the run rather than reading as a quiet week.
- **Linear.** `lib/linear.mjs`, one GraphQL call for the open issues of the active cycle (identifier, title, url, priority, due date, project), with `LINEAR_API_KEY`. Never fatal: without the key or an answer the customer lines of the mail fall back to HubSpot tasks, and `pulls.md` and the mail both say so.
- **The One Pager,** as text from the Drive export endpoint, the Atelic identity first and the personal one as the fallback. Not fatal when it fails; the failure is named in `pulls.md` and under the report's unverified list.
- **The sites.** For every name in bumps due, visits due, replies owed and tasks due, and the top eight first touch candidates, one capped file per domain: what the head of the home page code says (title, description, canonical, structured data types, the tells and third party hosts in the code, read out by `lib/text.mjs head`), `robots.txt`, then the home page and up to four internal pages as text with links kept. The raw home page HTML stays beside it for a claim that needs the code. One file per site because the first two runs spent most of their turns opening small files one at a time. A fetch is not a walk, and the prompt says so: nothing a page shows or fails to show becomes a finding on its own.

Then a write probe (`runner_probe_write`, a one line Haiku call with the same agent and allowlist, about a cent) proves the agent can write into the work directory, because the first two runs in the image drafted a whole week and then could not write it: the agent's definition listed no Write tool, and a path scoped Write rule is denied by `claude -p` in every form tried (relative, absolute, `//` prefixed, `*` and `**`), so the rule is the bare `Write`, safe in a container whose checkouts are read only mounts. Then one headless call runs the agent with the pulled files named in `prompt.md`. It sorts the week into its fixed order, gives every name owed a first touch, a bump, a visit or a drop off its line and a payload for the Outreach cloud routine (which drafts every touch since 2026-10-01), flags every reply owed for the desk to draft in the thread's own register, drafts nothing itself, and writes the roster as a complete file to `out/YYYY-Www-roster.md`, the skeleton's Placed Ahead section carried over at the foot. It returns one JSON summary (`prompt.md` carries the shape) and the node renderer in [../email/](../email/) renders it.

**The mail is a to do list, and its order is not the model's** (ATE-630, 2026-10-07). Forni opened the W41 mail on 2026-10-06, met dozens of MQL names in stage cards, and could not tell which of them needed him. It was a to do list problem wearing a report, so the mail is two things now, and `lib/pipeline.mjs` fills both from the records after the model returns:

- **Needs You Now**, one numbered list in his own order. First the named lines, each a sentence in four parts (who, what is owed, by when, a link): paying customers in build, trade customers in build, customers in operate, open proposals, warm SQLs in a live conversation, then replies owed. Then the cold end as a count per kind with its people a line each beneath: second touches to people who opened, first touches against the weekly target, visits, second touches to people who have not opened, and the names to close or keep. The heading counts the named lines alone.
- **Funnel Health**: the stage strip with each stage's week over week change, how many names entered and left each stage, and the last four send weeks, newest first, with tracked sends, opens, responses and both rates, each number carrying its change on the week before.

Under those sit a **Cloud Routines** table (how many of each routine's payloads fired, and by name only the ones that did not) and **The Groom** (one sentence counting its moves, and Left for You: what the groom could not settle, the model's flags, and any line the runner adds about its own reads). One footer line carries the run's duration, cost, turns and models.

**Where each line comes from.** The customer tiers are the open issues of the active Linear cycle (`lib/linear.mjs`, one read only GraphQL call) in the project a Customer company names in its HubSpot `linear_project` property; the won deal's `engagement_phase` says build or operate (build when unset), and a company is paying when its won deals sum to more than nothing and a trade otherwise. Proposals are every open deal, larger first, with the company's nearest open task as what is owed. Warm SQLs are live SQL companies with a task due or overdue or a touch the sweep reads as owed; a name parked past this week stays out. Replies are the model's `owed.reply`, its note printed as what is owed. Anyone a named line covers is taken out of the counted names, so nobody is listed twice. **When Linear cannot be read** (no key, a tracker that did not answer) the run goes on: the customer lines fall back to open HubSpot tasks on Customer companies and Left for You says the read did not run. A Customer with no `linear_project` falls back the same way and is named there.

**What the send weeks count.** One send per company per Denver day, tracked sends only (an untracked send has no open to read, so it is in neither side of either rate), to companies that were not yet an Opportunity or a Customer when the send went out; lifecycle Other never reaches the sweep. Opened is a tracked send with at least one open. Responded is a tracked send whose own thread carries a real inbound message after it, with the sweep's noise list (calendar traffic, autoresponders, invoices) already applied. The flag above the table is a sentence when the latest complete week has at least ten tracked sends and opened fifteen or more below the average of the three weeks before it; both numbers are named constants in `pipeline.mjs` and a starting point.

**The email is the two minute read and the roster is the long one** (2026-09-24, after the first W39 mail carried every per name note, every flag's full note and sixteen fold items inline, and Forni read it as too dense to run unattended): the per name notes, each flag's full note, the could not verify list and the names left off on purpose all live in the roster, the last two as its closing sections, and nowhere in the mail.

**The runner places the roster itself, and the mail links it** (2026-09-29; for two weeks it rode as an attachment that never got placed, and the W40 block ran off the mail while the repo still held the skeleton). Once the agent has written the roster and the summary passes, the entrypoint copies it into the Atelic clone as `Outreach/YYYY-Www-roster.md`, commits it as `Claude <claude@atelic.me>`, and pushes straight to main over a second, write capable deploy key (`ATELIC_PUSH_KEY`, the vault's `github-deploy-key-atelic-push`; the read only key still does the clone, and the agent never sees either). Prose lands direct to main in that repo by its own rules, and the repo's markdownlint runs on the push as an alarm, so the prompt tells the agent the file has to lint clean. One rebase onto a moved main is the whole retry. The mail then carries the file's GitHub link as the last line of the read card and no attachment. When the roster could not be placed (no push key, a push that failed twice, or a checkout this run did not clone, which is every local run since `mounts` puts this machine's real repo there read only), it rides as the attachment it used to be and the log says why, so the week is never lost:

```bash
cp runners/plumber/out/2026-W38-roster.md ~/Eudaimonia/Craft/Vocation/Atelic/Outreach/   # the by hand fallback, local runs only
```

**Then the runner fires the Outreach routine for every first touch and bump** (Forni, 2026-10-06: the rule said the desk fires it, and in W41 nobody did, so that week's drafts existed only as HTML in the roster file). Once the roster is placed or attached, the entrypoint reads the `payloads` array from the agent's summary, keeps only the entries whose `touch` is `first_touch` or `bump` (a reply is answered at the desk, a visit is walked, and neither ever fires), and posts each one's `text` to the routine's API trigger exactly as Atelic's `plugins/atelic/skills/handle-sighting/routine.md` documents, thirty seconds apart (`FIRE_SPACING`), since every fire is its own cloud session of three to five minutes. The summary is the source rather than the roster file because it already arrives as checked JSON with the business and the touch kind named, where the roster would have to be parsed back out of prose; the prompt tells the agent each entry's text is its roster line's fenced `text` block, verbatim. The token is `OUTREACH_TRIGGER_TOKEN`, from the vault's `atelic-keys/outreach-trigger-token`, and the routine's id is the plain `OUTREACH_ROUTINE_ID`; without either, nothing fires and the card says so. `DRY_RUN=1`, which every local run without `--send` sets, prints what would fire and fires nothing. Every payload is recorded in the summary as `drafting` (business, touch, outcome, HTTP status, and the session the API names), and the mail carries it as the Outreach row of its Cloud Routines card, naming only the payloads that did not fire, so Tuesday opens on the `matt@atelic.me` Drafts knowing which drafts to expect. A fire is never fatal: a payload that did not go out is still on the roster, and the desk fires it by hand. A rerun with `--reuse --send` fires again; the routine's dedupe reads `in:drafts`, so a second draft for the same business is caught there rather than here.

**What stays out, for now.** The browser walk. The method already says machine verified is not verified and that the Google captures for a bump come from Forni's own browser, so the runner writes each payload from the pulled evidence and marks on the roster line which claims still need a capture; the draft fires without them, and the Tuesday block rechecks those claims before the send. Putting Chromium in the image is a follow up once this version has run a few weeks. The HubSpot writes (auditing a prospect, parking a name) stay interactive too; those are things Forni asks for by name.

Prep only, for the agent: it never emails anyone, never moves a Lead Status, never posts to a client surface, and here it has no `hs`, no `gws`, no browser and no git at all. The run around it does write, in four places: the sweep's groom moves the stages and statuses the record already justifies (`SWEEP_GROOM=0` makes it read only), the entrypoint pushes the roster, fires the routine, and mails the report. Every send waits for Forni's explicit yes inside the Tuesday block, one at a time, through `/atelic:handle-outreach`.

It reports to `matt@atelic.me`, not the personal Gmail account, because this is Atelic work. Locally that comes from `~/.config/headless-report/recipient-plumber`.

## Running It

```bash
bin/runner/run-local plumber --week 2026-W38 --no-open   # in the image: pulls, one model call, renders to out/, sends nothing
bin/runner/run-local plumber --reuse                      # skips the pulls, one model call over the files already in out/
bin/runner/render-local plumber                           # re-render out/plumber.json, no network, no model
bin/runner/run-local plumber --send                       # the real thing, from this machine
```

A local run builds the image and runs it with Docker Desktop, and mounts this machine's `~/Eudaimonia` read only at the container's `/home/runner/Eudaimonia` (`mounts`), so the agent's `~/Eudaimonia/...` paths resolve there, the Atelic repo is found nested inside it, and no deploy key is needed on this machine. The work directory is `runners/plumber/out/`, which is also the agent's scratch directory: `portal.md`, `portal-detail.md` and `portal.json` the sweep, `mailbox.md` and `mailbox.json` the mailboxes, `one-pager.md`, `pulls/sites/<domain>.md` the site text, `pulls.md` what was pulled and what failed, `plumber.json` the summary, `email.html` the render, and `YYYY-Www-roster.md` the roster (the attachment, on a local run).

**Credentials.** `bin/runner/fetch-env plumber` reads the deployed job's secret mapping into `runners/plumber/.env.local`; before the job existed the file was written by hand: `HUBSPOT_SERVICE_KEY` from the Keychain (`hubspot-service-key-atelic`), and `GWS_OAUTH_TOKEN_ATELIC_JSON` and `GWS_OAUTH_TOKEN_PERSONAL_JSON` from `gws auth export --unmasked` under each profile. Mode 600, gitignored, never printed.

## What It Reads

The agent definition is `.claude/agents/plumber.md`, copied into the image by the staged build context (`agents`), and it names its own sources of truth: the method, the voice, the ICP statement in the One Pager, HubSpot, and the board. This runner adds only `prompt.md`: the week, the checkouts, the pulled files and which steps they already cover, the scratch directory, the roster's destination, and the JSON shape the renderer reads. The method itself lives in the agent. The model and effort are the agent's own (`model: opus`, `effort: medium`) unless `RUNNER_MODEL` names another, which is how the side by side is run (`RUNNER_MODEL=sonnet bin/runner/run-local plumber --reuse`).

## Failure

The report is mailed on failure as well as success, as the shared failure page: the reason on top and the last lines of the log beneath it, permission denials included. A run that cannot deliver its report exits non zero so the log carries it. A failed run keeps its `out/result.json`, so `render-local` and a read of the log are how a failure gets looked at without paying for the agent again; a pull that failed fails before the model is called, so it costs nothing.
