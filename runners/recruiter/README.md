# The Recruiter Runner

Pulls the job boards, runs the `recruiter` agent headlessly over what was pulled, so the week's sweep is done before the Tuesday 07:00 work search block opens, and mails the board as `YYYY-Www Recruiter` (the subject was `Sweep` until 2026-09-15: "I had no idea what Sweep was when it arrived"). A Cloud Run Job (`recruiter`, project `atelic`, region `us-central1`) fired by Cloud Scheduler every Monday at 23:00 Denver, in production since 2026-09-11; `bin/runner/run-local recruiter` stays the way to iterate on it.

**What the email is.** Forni's design ("W38 Sweep Email", Claude Design, 2026-09-11): cream ground, the atelic masthead, a title card with a two line headline, a lede, and three counts (shortlisted, for your call, verified and killed); one card per shortlisted role with the fit in orange, the title, comp and arrangement on one line, why it cleared, what the company does folded under a disclosure, and the posting link; **For your call**, the escape hatches the brief names (a growth engineering title that missed a hard filter, a hub hybrid outlier) with what each missed where the fit would sit, above the fold where they cannot be read past (added 2026-09-15 after Project Canary and C.Scale were both buried in the rejected list and Forni pulled them out himself); the fractional lane in the same shape with the rate where the fit sits, the a16z prospects line, and the claim tradeoff once; then "If you want to dig in", where the considered and rejected list and the source notes fold away. One footer line carries the run's duration, cost, turns and models. **The ledger rows are not in the email.** They go to the Pinole work API (below) and nowhere else; the markdown attachment that duplicated them as a fallback was dropped 2026-09-23. The agent returns the board as JSON (`prompt.md` carries the shape) and the node renderer in [../email/](../email/) renders it; the Tuesday block picks from the shortlist and hands the picks to `assist:draft-applications`. The disclosures fold in Apple Mail and open flat in Gmail, which is the designed fallback.

**The ledger lives in the Pinole work API, and the runner is what talks to it** (2026-09-16), through the `pinole` CLI the image installs from the public `atelic-action/pinole-cli` repo, pinned to a tag. Three calls per run, none of them the model's. Before the model starts, `pinole work postings list --all --table` writes every posting ever judged, any status, to `ledger.md` in the work directory, which is the seen set the prompt tells the agent to dedupe against; a failed pull is a failed run, never a skip, because a sweep without its seen set re verifies every posting at ATS cost and reports last week's rejections as new. After the model returns and the board has its shape, the ledger rows become `postings.json` (`date` to `first_seen_on`, `role` to `title`, `fit` to `fit_score`; `company`, `key`, `board`, `track`, `status`, `verdict` and `url` pass through) and `pinole work postings upsert --file` sends them; the API matches by key, then fuzzily on company and title, and a sweep status never overwrites an applied one. Then one `listings_review` activity is logged for the day, worded like the backfilled rows (the source list as the employer, what the sweep did as the channel), so the weekly claim reads it like every earlier sweep; a rerun on the same day finds the row already there and leaves it alone. The upsert and the activity log are hard failures too, but by then the draft is saved and nothing the model produced is lost. **All three calls happen in dry runs as well**, because a rehearsal that skips them proves nothing; only the email send honors `DRY_RUN`. The API answers land in `upsert.json` and `activity.json` beside the log.

The token is `PINOLE_API_TOKEN`, the vault secret `pinole-mcp-token` in `atelic-keys`, the same one the CLI reads from the Keychain on this machine (`bin/runner/lib.sh` fills it from there for a local run). The deployed job does not carry it yet, and the work domain is not deployed either; when both are, grant it the way the other three were:

```bash
gcloud run jobs update recruiter --project=atelic --region=us-central1 \
    --set-secrets=PINOLE_API_TOKEN=projects/<atelic-keys project number>/secrets/pinole-mcp-token:latest
gcloud secrets add-iam-policy-binding pinole-mcp-token --project=<atelic-keys project> \
    --member="serviceAccount:sweep-runner@atelic.iam.gserviceaccount.com" --role=roles/secretmanager.secretAccessor
```

`bin/runner/fetch-env` reads the mapping back from the job, so `.env.local` picks the new variable up on its next run with no change of its own.

**The runner fetches; the model reads.** Since 2026-09-15 (ATE-543) the entrypoint pulls every fetchable source with curl before `claude -p` starts, the retro's shape: the Getro tier (seven boards, the six software title queries, 42 fetches, six at a time, about twenty seconds), Tech Jobs for Good, Fractional Jobs, and the a16z Jobs feed. `text.mjs` reduces each page to what the model needs: a Getro board's listings come out of the `__NEXT_DATA__` state the page embeds, as clean JSON with the job id, title, employer, locations, work mode, seniority, comp, posting date, and the employer's own posting URL, so nothing is scraped from markup; a plain board becomes text with its links kept; the feed becomes one markdown file per issue with an index. `listings.jq` then folds the Getro pulls into `listings.md`: every board and query, deduplicated on job id, the deny list (`deny.txt`, the list of record the agent's brief points at) applied so a deny listed card never reaches the model, and what it dropped reported at the top. A board page carries only the first twenty results for a query and honors no paging parameter, which is the same view the model had when it fetched; the pull table's Total column says when a query had more. A fetch that fails is recorded in `pulls.md` and reported under the email's sources, never fatal; only the whole tier failing aborts. The ATS verification in step 3a stays the model's, one curl per candidate, because which calls to make depends on what survives the filters. WebFetch is no longer in the agent's tools here.

**The recruiter stays on Sonnet, and the cost lever was structural.** The first board (Sonnet, 2026-09-11) cost 6.64 USD list equivalent on the subscription token, 296 turns, 37 minutes, and the first production fire 4.99 USD in 156 turns; almost all of it was cache reads, one model turn per fetch. A same week side by side on Haiku cost 0.88 USD in 60 turns and eight minutes, and was cheaper because it skipped the verification step the method exists for: no employer side posting read, comp "TBD", the board named where the link should be, one shortlisted role (Geli) that Sonnet had rejected as stale and onsite, four open fractional roles missed because no detail page was fetched, five ledger rows against twenty. A board that hands the Tuesday block a role that does not exist costs more than it saves. **With the pulls moved into the entrypoint (2026-09-15, the W38 board reproduced in the local container): 2.33 USD, 62 turns, 7 minutes 29 seconds, against 4.99 USD, 156 turns and about 25 minutes for the same week's production fire the night before.** The board came back with the same two shortlisted roles (UtilityAPI, and the Shifted Energy posting followed to its acquirer Resource Innovations) plus Project Canary and C.Scale, the two the recruiter's rules had wrongly buried; the rest of the turns are the ATS verification, which is where the quality lives and stays on the model.

**The agent is read only, by construction.** It gets Read, Grep, Glob, WebSearch, curl, jq, and a scratch directory; no write reaches the Eudaimonia checkout, and the agent never calls the API. The runner makes the writes, from rows the agent returned. It reports to the personal mailbox, since the work search is personal work.

## Running It

```bash
bin/runner/run-local recruiter --week 2026-W38 --no-open   # in the image: pulls, one model call, renders to out/, sends nothing
bin/runner/run-local recruiter --reuse                      # skips the pulls, one model call over the files already in out/
bin/runner/render-local recruiter                           # re-render out/recruiter.json, no network, no model
bin/runner/run-local recruiter --send                       # the real thing, from this machine
```

A local run builds the image and runs it with Docker Desktop, and mounts this machine's `~/Eudaimonia` read only at the container's `/home/runner/Eudaimonia` (`mounts`), so the agent's `~/Eudaimonia/...` paths resolve there and no deploy key is needed on this machine. The work directory is `runners/recruiter/out/`, which is also the agent's scratch directory: `pulls/` holds every page and pull record, `listings.json` and `listings.md` the reduced tier, `pulls.md` what else was fetched, `recruiter.json` the board, `email.html` the render, and `ledger.md`, `postings.json`, `upsert.json` and `activity.json` the Pinole side. A local run needs the Pinole token like any other secret (Keychain `pinole-mcp-token`), dry run or not.

## What It Reads

The agent definition is `.claude/agents/recruiter.md`, copied into the image by the staged build context (`agents`), and it names its own sources of truth: the plan, the profile, the rubric, the work search log, and the sweep ledger. This runner adds only `prompt.md`: the week, the checkout, the pulled files and which step they already cover, the scratch directory, and the JSON shape the renderer reads, which replaces the markdown report the agent writes by hand; the method itself lives in the agent. The model and effort are the agent's own (`model: sonnet`, `effort: medium`), so the sweep that runs here is the sweep that runs by hand, minus the fetching.

## Promoting It

Promoted 2026-09-11: a Cloud Run Job `recruiter` in the `atelic` project (named `sweep` until 2026-09-15, when the runner, its job, its scheduler entry and its image all took the agent's name) under its own service account with three vault secrets injected (`atelic-keys/claude-code-oauth`, `atelic-keys/resend-api-key`, `forni-keys/github-deploy-key-eudy`; `atelic-keys/pinole-mcp-token` joins them when the work domain deploys, the command shape is above), `REPORT_RECIPIENT` set to the personal mailbox, and a Cloud Scheduler entry `recruiter` at `0 23 * * 1` Denver. `bin/runner/promote recruiter` rebuilds and repoints the job after a change. The runtime one pager for the pattern is Eudy's `Admin/Tools/cloud-run.md`. The job, the scheduler entry, the image and this directory are all `recruiter`; only the service account keeps its original `sweep-runner` name, since a service account cannot be renamed.

## Failure

The report is mailed on failure as well as success, with the reason on top and the last lines of the agent's output beneath it. A run that cannot deliver its report exits non zero so the log carries it. A failed run keeps its `out/result.json`, so `render-local` and a read of the log are how a failure gets looked at without paying for the agent again.
